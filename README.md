# Campaign Site Factory — تسليم التنفيذ (Execution Handoff)

هذا التسليم ينفّذ الـ PRD بترتيب الأولوية الذي حدده الملف نفسه (§13/§16): المرحلة 1 أولاً
(كاملة وقابلة للنشر)، ثم أساسات المرحلة 2 (كاملة وقابلة للنشر)، ثم محرك المصنع (Factory
Engine) نفسه (كود كامل، يحتاج اختبارًا حيًا بمفاتيحكم الحقيقية قبل الإنتاج).

```
campaign-site-factory/
├── tenant-template/     ← الموقع المشترك (المرحلة 1 + أساسات المرحلة 2) — جاهز للنشر
│   ├── index.html
│   ├── admin.html
│   ├── api/[...path].js
│   ├── sw.js
│   ├── vercel.json
│   ├── package.json
│   └── migrations/
│       ├── 001_base_schema.sql          (الأصلي كما هو)
│       └── 002_share_platforms_and_site_settings.sql   (جديد، إضافي بالكامل)
└── factory/              ← لوحة تحكم المصنع + محرك التزويد (المرحلة 2) — يحتاج ربط حقيقي
    ├── dashboard.html
    ├── api/[...path].js
    ├── lib/
    ├── migrations/001_factory_schema.sql
    ├── tenant-migrations/   (نسخة من migrations/ أعلاه، تُستخدم أثناء التزويد)
    └── README.md            (تعليمات الإعداد والتشغيل التفصيلية)
```

## ما تم تنفيذه فعليًا (وجاهز للنشر اليوم)

### المرحلة 1 — مشاركة واتساب وفيسبوك ✅
- زر مشاركة عبر واتساب (`wa.me`) وفيسبوك (`sharer.php`) بجانب X، على بطاقة كل تغريدة وفي نافذة المشاركة، بألوان العلامات التجارية الرسمية.
- كل زر يظهر فقط إن كانت منصته مفعّلة (`isPlatformEnabled`) — جاهز لتفعيل/تعطيل لكل جهة لاحقًا دون تعديل كود.
- كل نقرة مشاركة تُسجَّل بمنصتها في `analytics_events.platform`، مع ترحيل آمن للقواعد التي لم تُطبَّق عليها الهجرة بعد.
- لوحة الإدارة تعرض توزيع المشاركات حسب المنصة (إجمالاً وحسب كل حملة).
- وسوم Open Graph مضافة في `<head>` حتى تظهر معاينة صحيحة عند المشاركة على فيسبوك/واتساب.
- **لم تُحذف أو تُعدَّل أي وظيفة موجودة** — تم فقط اكتشاف وإصلاح خلل موجود مسبقًا (زر `confirmShare()` في نافذة المشاركة كان يستدعي دالة غير معرّفة، أي أن النافذة كانت معطوبة أصلاً وغير مستخدمة في الواجهة الفعلية؛ تم ربطها بشكل صحيح كأثر جانبي لإضافة الأزرار الجديدة).

### أساسات المرحلة 2 — الهوية الديناميكية والأمان ✅
- `GET /api/config`: نقطة عامة بدون مصادقة تُرجع اسم الجهة/الشعار/الألوان/المنصات المفعّلة من جدول `site_settings` الجديد، مع رجوع آمن للقيم الحالية المثبّتة بالكود إن لم يوجد الجدول أو الصف بعد — **الموقع الحيّ لن يتغير سلوكه إطلاقًا حتى تُنشئوا صفًا فعليًا**.
- `sw.js` يقرأ اسم/شعار الجهة من `/api/config` عند كل إشعار push، بنفس منطق الرجوع الآمن.
- جدول `main_admins` جديد + مسار مصادقة إضافي في `handleAuth`: يُفحص أولاً (PBKDF2 + salt، نفس آلية المشرفين الفرعيين)، ثم يرجع لمتغيرات البيئة `ADMIN_USER`/`ADMIN_PASS` فقط إن لم يوجد صف — هذا ينفّذ بند الأمان §11-4 دون كسر أي نشر حالي.
- قفل حساب مؤقت بعد 5 محاولات فاشلة (بند §11-7)، فوق آلية تحديد المعدّل بالـ IP الموجودة أصلاً.
- دعم `mustChangePassword` في استجابة تسجيل الدخول (بند §11-8).
- CSP + HSTS في `vercel.json` (بند §11-6، كانا غائبين تمامًا كما رصد الـ PRD).

⚠️ **ملاحظة صادقة حول الـ CSP**: لأن الموقع يعتمد على Tailwind CDN وAlpine.js (الذي يستخدم `new Function` داخليًا لتقييم التعبيرات)، الـ CSP المضافة تحتاج `'unsafe-inline'` و`'unsafe-eval'` لتعمل دون كسر الموقع. هذا تحسين حقيقي (يمنع تحميل سكربتات من نطاقات غير مصرَّح بها) لكنه ليس CSP صارمة بالكامل. التحصين الكامل يتطلب الانتقال من Tailwind CDN/Alpine إلى خطوة بناء (build step) — أقترح إدراج هذا ضمن المرحلة 3 أو 4.

## ما تم بناؤه ويحتاج اختبارًا حيًا قبل الاعتماد عليه (محرك المصنع، `factory/`)

كل الكود التالي **مكتمل بنيويًا ومفحوص صياغيًا (`node -c` على كل ملف)**، لكنه يتفاعل مع Vercel
REST API وSupabase Management API الحقيقيتَين، ولا تتوفر لي بيئة شبكية لاختبار الاستدعاءات
الفعلية. تم التحقق من شكل نقاط النهاية (endpoints) عبر بحث ويب مباشر أثناء الكتابة (إنشاء
مشروع، متغيرات البيئة، النطاقات، تشغيل SQL)، لكن يُنصح بمراجعة `factory/README.md` §3 قبل أول
تشغيل فعلي — هناك قائمة تحقق واضحة بالنقاط الأكثر عرضة للتغيير (خصوصًا إصدار نقطة نشر Vercel،
ونظام مفاتيح Supabase الجديد الذي في طور الاستبدال).

المُنفَّذ:
- **قاعدة بيانات المصنع الكاملة** (`tenants`, `provisioning_jobs`, `super_admins`, `factory_activity_logs`, `secrets_vault`, جلسات) — §9-أ بالكامل.
- **خزنة الأسرار** (`lib/secretsVault.js`): تشفير AES-256-GCM حقيقي، مُختبَر ويعمل — §11-1.
- **مصادقة ثنائية (TOTP)** بدون أي اعتمادية خارجية (`lib/totp.js`) — تم اختبارها ضد متجهات اختبار RFC 6238 الرسمية ونجحت — §11-3.
- **عميل Vercel API** و**عميل Supabase Management API** (`lib/vercelClient.js`, `lib/supabaseManagementClient.js`) — إنشاء/حذف مشاريع، متغيرات بيئة، نطاقات، تشغيل SQL.
- **محرك التزويد** (`lib/provisioning.js`): تنفيذ خطوات §7-ب الاثنتي عشرة، مع تسجيل حالة كل خطوة، وRollback تلقائي عكسي عند أي فشل (حذف كل ما أُنشئ جزئيًا) — يلبي متطلب §14 (عدم ترك موارد يتيمة).
- **واجهة API الكاملة للمصنع** (`factory/api/[...path].js`): تسجيل الدخول + التسجيل الثنائي، إنشاء/تعليق/استئناف/حذف جهة (بتأكيد مزدوج فعلي عبر مطابقة الـ slug)، كشف كلمة مرور الأدمن لمرة واحدة، إعادة تعيينها، تحديث القالب لجهة واحدة أو لكل الجهات، سجل تدقيق.
- **لوحة تحكم المصنع** (`factory/dashboard.html`): تسجيل دخول + تسجيل 2FA بصورة QR، قائمة الجهات مع الإجراءات، معالج إنشاء بخطوات §7-أ الستّ مع معاينة حيّة، متابعة تقدّم حيّة (polling)، سجل تدقيق.

غير مُنفَّذ عمدًا (يحتاج قرارًا/بنية تحتية منكم تحديدًا):
- **قائمة الانتظار غير المتزامنة الحقيقية (Job Queue)**: التنفيذ الحالي يستدعي خط الأنابيب مباشرة من نقطة الإنشاء، بحد أقصى للتنفيذ `maxDuration: 300` ثانية (يتطلب خطة Vercel تدعم هذا). للإنتاج الفعلي على نطاق واسع، أوصي بتحويلها إلى Vercel Cron يستدعي خطوة واحدة في كل استدعاء (`lib/provisioning.js` مبني بالفعل كخطوات منفصلة قابلة للاستئناف تحقيقًا لمتطلب "Idempotent" في §12) — موثّق بالتفصيل في `factory/README.md`.

## قرارات §15 المؤجلة — الافتراضات التي اعتمدتُها

نفّذت المرحلة 2 بالافتراضات نفسها التي حددها الـ PRD كافتراضي عند عدم الحسم:

1. **تعديل الهوية بعد الإنشاء**: من لوحة المصنع فقط حاليًا (لا توجد نقطة API في `admin.html` لتعديل `site_settings` تلقائيًا بعد — يمكن إضافتها لاحقًا بسهولة إن قررتم فتحها لأدمن الجهة).
2. **النطاقات**: نطاق فرعي تحت نطاقكم فقط (`TENANT_BASE_DOMAIN`) في هذا الإصدار؛ لا دعم نطاقات مخصصة بعد.
3. **فترة سماح قبل الحذف النهائي**: **لم تُنفَّذ** — الحذف الحالي فوري بعد التأكيد المزدوج. هذا القرار لم يكن له افتراضي واضح في الـ PRD، فتركته كما هو (بدون فترة سماح) لتُقرروا صراحة. إضافتها بسيطة: تغيير `handleDeleteTenant` ليُعلّق الجهة أولًا (`status='deleting'` + `scheduled_deletion_at`) بدل الحذف الفوري.

## الخطوات التالية المقترحة

1. **قبل أي شيء**: راجعوا `factory/README.md` §1 و§3، وشغّلوا خط الأنابيب كاملاً على جهة تجريبية وهمية واحدة — هذا نص تعليمات الـ PRD نفسه (§16) وهو الأهم فعليًا قبل الاعتماد على أي من كود `factory/`.
2. نشر `tenant-template/` كتحديث للموقع الحيّ (المرحلة 1 + أساسات المرحلة 2) — منخفض المخاطر، كل شيء رجوعه آمن.
3. تشغيل `factory/migrations/001_factory_schema.sql` على مشروع Supabase جديد مخصص للمصنع، ثم اتباع خطوات الإعداد في `factory/README.md`.
4. المرحلة 3 (إعادة التصميم + الأنيميشن) والبنود المتبقية من المرحلة 4 (تدوير خوارزمية التجزئة إلى Argon2id، فحص الاعتماديات الدوري) لم تُنفَّذ بعد في هذا التسليم — جاهز للمتابعة عند الطلب.
